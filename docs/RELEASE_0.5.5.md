# 0.5.5 发布记录：写作语义重试反馈

## 触发原因

0.5.4 真实金丝雀把旧 Step 5 完成记录安全重验后，准确发现正文中 5 处未转义 `VERIFY_DATA`。第一次重跑仍使用原始 Step 5 Prompt，模型回合正常完成但没有改动 `draft_v2.tex`；产物新鲜度门禁以 `WRITING_EXPECTED_ARTIFACT_STALE` 正确拦截，没有错误推进状态。

这说明“发现旧产物问题”与“把确定性验证反馈带入重试上下文”之间还缺少一条受控链路。

## 修复

- 原始用户调优 Prompt 文件继续保持原字节不变，并仍是步骤语义的唯一权威来源。
- 只有当前产物与记录的静态重试基线逐字节一致、固定线程和失败回合证据完整、当前验证器仍返回受支持问题时，stale 回合才允许显式重排。
- 验证器问题先映射到代码内固定的 issue-code/规范消息白名单，再生成独立、限长、一次性的重试反馈信封；journal 中的任意自由文本都不会拼入模型指令。
- 重排时、取得会话许可后和真正发送回合前都会绑定并复核同一份产物字节；期间被人工修改、已经修好、验证结果漂移或原 Prompt 哈希缺失时均零调用停止。
- 重试意图、反馈信封和执行哈希会在离开 `retry_ready` 前一起持久化；即使进程在发送前中断，恢复后仍只会向同一固定会话发送一次相同反馈。
- 完成记录重验改用持久 redo 事务标记协调 SDK journal 与写作 pipeline：任一写入边界发生硬崩溃后，下次启动会在双锁下幂等恢复；未知或冲突字节保持阻断，模型不会启动。
- 普通首次执行不带反馈；反馈不改变 Prompt 源文件哈希，也不放宽产物新鲜度、语义验收或真实证据门禁。

## 真实边界

重试反馈只帮助同一个固定会话修复已经由本地验证器证明的问题。它不会生成实验数据，不会把 `【验】` 或模拟结果当作真实证据，也不会绕过 Step 5→6 的证据门禁。
