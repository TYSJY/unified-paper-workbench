# 0.5.2 发布记录：写作阶段可靠性修复

## 修复结果

- 每个 Codex SDK 回合同时在会话和回合层声明 `workspace-write` 与拒绝交互式审批，修复授权成功却无法写文件的问题。
- Step 1 严格串行分配论文编号；已绑定论文的后续步骤仍按配置并发，全部可检测主会话与子会话共享 10 个加权容量。
- 容量不足不再把任务永久留在等待状态；本地容量释放立即唤醒，外部容量按低频、无模型 Token 的方式重新检查。
- 用户在等待 Step 1 锁、并发槽或容量时暂停，调度器会在真正发送前再次检查，不会偷跑新回合。
- 进程中断后若固定会话仍在运行，调度器会低频读取同一回合直至终态，并使用原派发基线验收，绝不重复发送。
- 阻塞、等待、暂停、运行和完成状态同步到任务、步骤、命令和界面；新建任务只在 Step 1 标记与产物均验证后才标为完成。
- 每一步在发送前记录全部预期输出基线；完成时要求每个输出均为本轮创建或内容更新，并拒绝 Step 1 覆盖、软链接、目录联接和 Windows 重解析路径。
- 同一批次中两篇不同论文出现同类执行、产物或线程基础设施故障后自动熔断；未发送任务安全暂停，下一次显式运行才会重新授权。正常的新颖性与实验证据业务门禁不触发此熔断。
- SDK 提供的每回合输入、缓存输入、输出、推理输出、总 Token 与上下文窗口统计会在产物验收前写入步骤审计，因此合同失败也保留用量证据。
- 新增精确 `paper_key` 与临时 `until_step` 金丝雀运行，以及必须显式选择、确认旧线程已归档的可恢复重排队入口。

## 不变项

- 不修改写论文、画图、选刊作者和投稿的任何内部 Prompt；发布前后继续执行原字节哈希合同。
- 不覆盖 Codex Desktop 的登录、配置或任务；写作 SDK 继续使用程序独立的 `state/codex_sdk_home`。
- 不启用旧写作 Automation，不修改旧投稿通道。

## 发布验收

- 发布版 EXE 必须通过完整隔离测试、Prompt 合同、版本探针、账号状态探针和精确金丝雀帮助入口。
- 真实任务先以一篇一阶段金丝雀验证写权限、产物新鲜度、固定线程和状态回写，再恢复其余队列。
